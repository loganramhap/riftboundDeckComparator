# Requirements Document

## Introduction

The Riftbound Deck Comparator is a self-hosted web application that lets a Riftbound player compare two decks side by side and see the card differences graphically. Each deck can be supplied in one of three ways: a pasted text deck list, a Piltover Archive deck code, or a URL to a decklist. The comparison treats different printings of the same card (for example base art, alternate art, or signed variants) as identical, so differences reflect actual card composition rather than cosmetic variation. Users can name each deck (or inherit names from a source link) and generate a shareable link that reproduces the exact comparison.

The application is intended to be deployed in an LXC container on Proxmox.

## Glossary

- **Comparator**: The web application system that ingests, normalizes, and compares two decks and renders the comparison.
- **Deck_Parser**: The Comparator subcomponent that parses a text deck list into a structured deck.
- **Deck_Code_Decoder**: The Comparator subcomponent that decodes a Piltover Archive deck code into a structured deck.
- **Link_Importer**: The Comparator subcomponent that retrieves a decklist from a supplied URL and produces a structured deck.
- **Deck_Normalizer**: The Comparator subcomponent that reduces card identity to a printing-independent form for comparison.
- **Comparison_Engine**: The Comparator subcomponent that computes the differences and commonalities between two normalized decks.
- **Share_Service**: The Comparator subcomponent that creates and resolves shareable comparison links.
- **Deck List (Text)**: A human-readable list of cards and quantities pasted by the user.
- **Deck Code**: A Piltover Archive encoded string representing a deck (format described by the RiftboundDeckCodes specification).
- **Card Code**: An identifier composed of a set identifier, a card number with an optional prefix (R for runes, SP for special cards), and an optional variant suffix (for example `OGN-007a`).
- **Printing**: A specific published version of a card distinguished by its variant suffix (for example base, alternate art, signed).
- **Normalized Card Identity**: A Card Code reduced to its set identifier and card number (including any number prefix), with the variant suffix removed, used for comparison.
- **Card Difference**: A card whose total quantity differs between the two decks, including cards present in only one deck.
- **Shared Card**: A card present in both decks at any quantity.
- **Shareable Link**: A URL generated by the Comparator that reconstructs a specific comparison.

## Requirements

### Requirement 1: Provide Deck Input by Multiple Methods

**User Story:** As a Riftbound player, I want to supply each of two decks by text list, deck code, or link, so that I can compare decks regardless of the format I have them in.

#### Acceptance Criteria

1. THE Comparator SHALL accept two decks per comparison, identified as the first deck and the second deck.
2. WHERE the user selects text-list input for a deck, THE Comparator SHALL accept a pasted Deck List (Text) for that deck.
3. WHERE the user selects deck-code input for a deck, THE Comparator SHALL accept a Piltover Archive Deck Code for that deck.
4. WHERE the user selects link input for a deck, THE Comparator SHALL accept a decklist URL for that deck.
5. THE Comparator SHALL allow the two decks to use different input methods within a single comparison.
6. IF the user requests a comparison while either deck has no input provided, THEN THE Comparator SHALL reject the request and return an error message identifying which deck is missing input.
7. IF the input provided for a deck does not match the format expected by the selected input method, THEN THE Comparator SHALL reject that deck's input and return an error message identifying the input method and the reason it was rejected.

### Requirement 2: Parse Text Deck Lists

**User Story:** As a Riftbound player, I want my pasted deck list parsed correctly, so that the comparison reflects the cards I entered.

#### Acceptance Criteria

1. WHEN a Deck List (Text) is submitted, THE Deck_Parser SHALL parse each non-blank line into a Card Code and an associated integer quantity, producing a structured deck that maps each distinct Card Code to its total quantity.
2. WHEN parsing a line of a Deck List (Text), THE Deck_Parser SHALL accept a line of the form "<quantity> <Card Code>" or "<quantity>x <Card Name>", where quantity is an integer from 1 to 99 inclusive and a Card Code matches the pattern SET-number with an optional single trailing variant letter (for example OGN-007a).
3. WHEN parsing a Deck List (Text) that contains multiple lines referencing the same Card Code, THE Deck_Parser SHALL sum their quantities into a single entry in the structured deck, capped at a maximum of 99 per Card Code.
4. WHEN parsing a Deck List (Text), THE Deck_Parser SHALL ignore blank lines and lines containing only whitespace, and SHALL exclude any card with a resulting quantity of zero from the structured deck.
5. IF a line of the submitted Deck List (Text) does not match an accepted format, has a quantity outside 1 to 99, or contains a Card Code that does not match the required pattern, THEN THE Deck_Parser SHALL reject the submission and return an error message identifying the specific line number and content that failed to parse, without producing a structured deck.
6. WHEN a structured deck is submitted for formatting, THE Deck_Parser SHALL format it into a Deck List (Text) containing one line per Card Code in the form "<quantity> <Card Code>".
7. WHILE processing any parseable Deck List (Text), THE Deck_Parser SHALL ensure that parsing, then formatting, then parsing again produces a structured deck equivalent to the first, where equivalent means the two structured decks contain identical sets of Card Codes each mapped to identical quantities.

### Requirement 3: Decode Piltover Archive Deck Codes

**User Story:** As a Riftbound player, I want to paste a Piltover Archive deck code, so that I can compare a deck shared in that format.

#### Acceptance Criteria

1. WHEN a valid Deck Code is submitted, THE Deck_Code_Decoder SHALL decode it into a structured deck that maps each Card Code to an integer quantity of 1 or more.
2. IF a submitted Deck Code is empty, malformed, or otherwise cannot be decoded, THEN THE Deck_Code_Decoder SHALL reject it and return an error message indicating that the Deck Code is invalid, without producing a structured deck.
3. WHEN a structured deck is submitted for encoding, THE Deck_Code_Decoder SHALL encode it into a Deck Code.
4. WHILE processing any structured deck that the Deck_Code_Decoder can encode, decoding then encoding then decoding SHALL produce a structured deck equivalent to the first, where equivalent means identical sets of Card Codes each mapped to identical quantities (round-trip property).

### Requirement 4: Import Decklists from Links

**User Story:** As a Riftbound player, I want to paste a link to a decklist, so that I can compare a deck without copying its contents manually.

#### Acceptance Criteria

1. WHEN a decklist URL from a supported decklist source is submitted, THE Link_Importer SHALL retrieve the decklist and produce a structured deck of Card Codes with associated quantities.
2. IF a submitted URL is not a well-formed URL or does not reference a supported decklist source, THEN THE Link_Importer SHALL reject the submission and return an error message identifying that the source is unsupported, without producing a structured deck.
3. IF the decklist is not retrieved from a supported URL within 30 seconds of submission, THEN THE Link_Importer SHALL abort the retrieval and return an error message indicating the retrieval failure.
4. IF the decklist cannot be retrieved from a supported URL, THEN THE Link_Importer SHALL return an error message indicating the retrieval failure and SHALL NOT produce a structured deck.
5. IF the content retrieved from a supported URL cannot be parsed into a structured deck containing at least one Card Code with a quantity of one or more, THEN THE Link_Importer SHALL treat the failure as a retrieval failure and return an error message indicating the retrieval failure.
6. WHEN a decklist is retrieved successfully from a supported URL that includes a deck name, THE Link_Importer SHALL extract the deck name from the source and associate it with the produced structured deck.
7. WHEN a decklist is retrieved successfully from a supported URL that does not include a deck name, THE Link_Importer SHALL produce the structured deck with no source deck name associated.

### Requirement 5: Normalize Cards Independent of Printing

**User Story:** As a Riftbound player, I want printings ignored during comparison, so that alternate art and signed cards are treated as the same card.

#### Acceptance Criteria

1. WHEN a structured deck is prepared for comparison, THE Deck_Normalizer SHALL produce a Normalized Card Identity for each Card Code by removing any trailing variant suffix while retaining the set identifier and the full card number, including any R or SP prefix.
2. WHEN a Card Code has no variant suffix (a base printing), THE Deck_Normalizer SHALL produce a Normalized Card Identity equal to that Card Code's set identifier and card number unchanged.
3. THE Deck_Normalizer SHALL treat two Card Codes that share the same set identifier and card number as the same Normalized Card Identity regardless of variant suffix.
4. WHEN multiple printings of the same Normalized Card Identity appear within one deck, THE Deck_Normalizer SHALL sum the quantities of those printings, as present in the deck data, into a single quantity for that Normalized Card Identity.
5. IF a Card Code does not match the expected pattern of a set identifier, a card number, and an optional variant suffix, THEN THE Deck_Normalizer SHALL reject that deck and return an error message identifying the malformed Card Code.

### Requirement 6: Compare Two Decks

**User Story:** As a Riftbound player, I want the differences and commonalities between two decks computed, so that I can understand how the decks differ.

#### Acceptance Criteria

1. WHEN two normalized decks are available, THE Comparison_Engine SHALL compute, for each Normalized Card Identity present in either deck, the quantity in the first deck and the quantity in the second deck from the actual deck contents.
2. THE Comparison_Engine SHALL classify each Normalized Card Identity as a Shared Card when the quantity in the first deck equals the quantity in the second deck, and as a Card Difference when the quantities differ.
3. THE Comparison_Engine SHALL include a Normalized Card Identity present in only one deck as a Card Difference, with a quantity of zero recorded for the deck in which the card is absent and the actual quantity recorded for the deck in which the card is present.
4. WHEN the two decks contain the identical set of Normalized Card Identities with equal quantities after normalization, THE Comparison_Engine SHALL report a count of zero Card Differences.
5. THE Comparison_Engine SHALL produce a comparison result whose set of Shared Cards and set of Card Differences is identical regardless of which deck is provided as the first deck and which is provided as the second deck, with each per-deck quantity attributed to the deck it originated from.
6. IF one or both decks are not available or cannot be normalized when a comparison is requested, THEN THE Comparison_Engine SHALL not produce a comparison result and SHALL return an error indication identifying that a valid normalized deck is missing.
7. WHEN a comparison is requested and one or both decks contain zero cards after normalization, THE Comparison_Engine SHALL complete the comparison and report every Normalized Card Identity present in the non-empty deck as a Card Difference with a quantity of zero for the empty deck.

### Requirement 7: Display the Comparison Graphically

**User Story:** As a Riftbound player, I want to see the differences graphically, so that I can quickly identify what changed between the decks.

#### Acceptance Criteria

1. WHEN a comparison result is available, THE Comparator SHALL display a graphical view that includes every Card Difference in the comparison result.
2. THE Comparator SHALL render each Card Difference with a visual indicator that distinguishes it from each Shared Card in the graphical view.
3. FOR EACH Card Difference, THE Comparator SHALL identify the card by its Normalized Card Identity in the graphical view.
4. FOR EACH Card Difference, THE Comparator SHALL display its quantity in the first deck and its quantity in the second deck, each attributed to the deck it belongs to.
5. THE Comparator SHALL display the name of the first deck and the name of the second deck in the graphical view, each associated with that deck's per-deck quantities.
6. IF a comparison result contains zero Card Differences, THEN THE Comparator SHALL display an indication in the graphical view that the two decks have no Card Differences.

### Requirement 8: Name the Decks

**User Story:** As a Riftbound player, I want to name each deck, so that the comparison is easy to read and reference.

#### Acceptance Criteria

1. THE Comparator SHALL allow the user to assign a name of 1 to 100 characters to the first deck and a name of 1 to 100 characters to the second deck.
2. WHEN a deck is imported from a link that provides a deck name and the user has not entered a name for that deck, THE Comparator SHALL use the name extracted from the source, truncated to a maximum of 100 characters, as that deck's name.
3. WHEN the user enters a name for a deck that contains at least one non-whitespace character, THE Comparator SHALL use the user-entered name, trimmed of leading and trailing whitespace, as that deck's name in preference to any name provided by the deck's source.
4. IF a deck has neither a user-entered name containing at least one non-whitespace character nor a name provided by its source, THEN THE Comparator SHALL assign the default name "Deck 1" to the first deck and "Deck 2" to the second deck.
5. IF the user submits a name for a deck that exceeds 100 characters, THEN THE Comparator SHALL reject the name and return an error message indicating the maximum allowed length, and SHALL retain the deck's prior name.

### Requirement 9: Create and Resolve a Shareable Comparison Link

**User Story:** As a Riftbound player, I want a shareable link to an exact comparison, so that I can send the comparison to others.

#### Acceptance Criteria

1. WHEN the user requests to share a comparison, THE Share_Service SHALL generate a Shareable Link that encodes the first deck's Card Codes and quantities, the second deck's Card Codes and quantities, the first deck name, the second deck name, and the comparison result.
2. WHEN a Shareable Link is opened, THE Share_Service SHALL reconstruct the first deck, the second deck, the first deck name, and the second deck name exactly as they were when the link was generated, preserving each deck name verbatim including its full character sequence.
3. FOR ALL comparisons for which a Shareable Link is generated, generating a Shareable Link and then opening it SHALL reproduce a comparison in which each Normalized Card Identity has the same per-deck quantities, the same classification as a Card Difference or Shared Card, and the same first and second deck names as the original comparison (round-trip property).
4. IF an opened Shareable Link is malformed or its encoded contents cannot be reconstructed into two decks and their names, THEN THE Share_Service SHALL return an error message indicating that the Shareable Link is invalid and SHALL NOT display a partial or altered comparison.
